# CI130X 音频移植与调试报告

> 目标板：`ycsc-esp32s3-8311-wgxl-cat`（ESP32-S3）
> 原方案：ES8311 Codec；新方案：CI1302 作为「智能 Codec」，通过 I2S + UART 接入小智框架
> 时间范围：本次会话全过程

---

## 1. 背景与目标

原始固件用 ES8311 做音频前端：ESP32 通过 I2C 配置寄存器、I2S 做主设备收发 PCM。

目标是把 CI1302（启英泰伦离线语音芯片）替换进来，利用它自带的：

- 麦克风采集与降噪
- 离线唤醒词（"你好小智"）
- 本地 VAD、离线命令词
- 功放与音量控制

ESP32 侧不再做音频采集，只负责：把 CI 送上来的 PCM 上传云端、把云端 TTS 下行 PCM 送给 CI 播放、以及通过串口同步状态。

## 3. 关键实现

### 3.1 I2S 从机配置

单端口全双工，关键参数（`ci130x_audio_codec.cc::CreateDuplexChannels`）：

```cpp
.id = I2S_NUM_0,
.role = I2S_ROLE_SLAVE,
.dma_desc_num = AUDIO_CODEC_DMA_DESC_NUM,   // 6
.dma_frame_num = 256,                       // 1024 字节/描述符
.auto_clear_after_cb = true,
```

Slot 配置：

```cpp
.data_bit_width = I2S_DATA_BIT_WIDTH_16BIT,
.slot_bit_width = I2S_SLOT_BIT_WIDTH_32BIT,
.slot_mode      = I2S_SLOT_MODE_STEREO,
.slot_mask      = I2S_STD_SLOT_BOTH,
.ws_width       = 32,
.bit_shift      = true,
.left_align     = true,
```

即 16 kHz / 16 bit / 双声道 / 32 bit slot（SCK:LRCK = 64），16 bit 有效数据左对齐放在高 16 位，与 CI 的 IIS 输出一致。左声道为 MICL。

### 3.2 UART 协议

16 字节帧头 + payload，magic `0x5A5AA5A5`，`checksum = Σpayload`，version `0x0100`，fill `0x12345678`。

用到的指令：

| 指令 | 码 | payload | 作用 |
|---|---|---|---|
| 系统就绪 | 0x0601 | — | CI 上报（事件） |
| 开始录音 | 0x011A | — | 置 `is_always_iis_flag`，I2S 持续出 PCM |
| 停止录音 | 0x011B | — | 清 `is_always_iis_flag` |
| 播放窗口 | 0x0220 | 1 字节 1/0 | 允许/禁止 CI 播放 |
| 音量 | 0x0117 | 1 字节 1~7 | 音量档位 |
| 退出唤醒 | 0x010D | 1 字节（1=提示音） | 强制 CI 退出唤醒态 |
| 唤醒态超时 | 0x0113 | uint16 秒 | 覆盖 CI 自动退出时间 |

事件：

| 事件 | 码 | 含义 |
|---|---|---|
| WAKE_UP | 0x0102 | 唤醒词触发 |
| VAD_START | 0x0108 | 检测到人声 |
| PCM_FINISH | 0x0106 | 一句话结束 |
| EXIT_WAKE_UP | 0x0109 | 退出唤醒态 |

应答统一 `0x0801`，payload `[type_lo, type_hi, 1=成功/2=失败]`。

### 3.3 状态同步策略

ESP32 维护三组「期望值 / 已生效值」：录音开关、播放窗口、音量。`SyncWithChip()` 逐项比对下发，后台 `SyncTask` 每 500 ms 收敛一次，失败退避到 10 s。

三个触发器：

- `EnableInput/EnableOutput/SetOutputVolume` 被框架调用时立刻同步；
- 收到 `SYS_READY`（CI 重启）→ 强制整组重发；
- 上行看门狗判定断流 → 重发 `0x011A`。

### 3.4 唤醒桥接与状态机

CI 的 `WAKE_UP(0x0102)` → 板级回调 → `Application::WakeWordInvoke()`，仅允许 `idle`（开新会话）和 `speaking`（打断播报）两种状态，其余状态忽略。

ESP32 回到 `kDeviceStateIdle` → `0x010D` 通知 CI 退出唤醒（静默，不带提示音）。

### 3.5 功放控制

`Ci130xAudioCodec` 新增 `pa_pin` / `pa_active_high` 参数，`EnableOutput()` 时按 `output_enabled_` 驱动：

```cpp
int level = output_enabled_ ? (pa_active_high_ ? 1 : 0)
                            : (pa_active_high_ ? 0 : 1);
gpio_set_level(pa_pin_, level);
```

配合框架的 15 秒音频电源超时，空闲时功放自动关闭。

## 4. 问题时间线与修复

| # | 现象 | 根因 | 修复 |
|---|---|---|---|
| 1 | 开机无声音、说话不识别，日志反复 `CI130X not ready yet` | `SyncWithChip()` 以「收到过 0x0601」为前提，而 CI 只在上电时上报一次，ESP32 晚启动必然错过 | 去掉 ready 门槛；加 `SyncTask` 后台收敛重试 |
| 2 | 崩溃 `Cache error / MMU entry fault` | 非音频协议问题（tcpip_thread 的 tlsf_malloc / gifdec） | 未根治，加内存观察、建议关 GIF 做 A/B |
| 3 | `Ringbuffer of AFE(FEED) is full` 刷屏 | `Read()` 无数据时立刻返回静音，输入任务以几十倍实时速度灌 AFE | `Read()` 内按采样率补齐节奏（`vTaskDelay`） |
| 4 | `I2S RX short read: 1920/2048 bytes` 每次都短读 | `dma_frame_num=240`（960 B/描述符）不整除 2048 字节读长度 | 改 `dma_frame_num=256`（1024 B），并只取实际收到的部分 |
| 5 | CI 自己唤醒后 ESP32 无反应 | ESP32 本地 `AfeWakeWord` 收到的是掉帧通道 | 加 `SetWakeWordHandler`，用 `0x0102` 事件桥接到 `WakeWordInvoke` |
| 6 | 完整对话后 `Brownout` 复位 | 功放启动电流冲击 | 硬件侧：5V/2A 电源、功放电源脚加 470~1000 µF + 0.1 µF；软件侧：降低音量档 |
| 7 | 时好时坏：有时怎么说都不识别 | ① 音频任务里同步等 300 ms ACK，阻塞导致 RX DMA 溢出丢开头；② CI 唤醒词常开，listening 时重复唤醒触发 `CloseAudioChannel()` 杀会话；③ CI 运行中重启，内部标志清零 | ① 后续改为异步/短超时；② 唤醒回调按状态过滤；③ 收 `SYS_READY` 强制整组重发 |
| 8 | 上行满字节但全 0，`rms=0` 不动 | CI 循环输出 zero_buffer（录音门控关闭），旧看门狗只看 `bytes_read==0` | 看门狗覆盖「全静音」；触发后解除武装，冷却 20~40 s 再重试 |
| 9 | `rms=2147483647` | 512 点 × 32767² 溢出 int32 | `sum_sq` 改 int64 |
| 10 | 电量播报/日志刷屏干扰调试 | 每秒播报 + 每秒 `ESP_LOGW` | 注释电量/充电 OGG；全局日志压到 ERROR，仅放行 4 个 TAG |

## 5. 当前行为（交付状态）

### 5.1 状态对应关系

```
CI 唤醒  → 0x0102 → ESP32: idle → connecting → listening
ESP32 待机 → kDeviceStateIdle → 0x010D → CI: 退出唤醒（静默）
ESP32 播放 → 0x0220 = 1 → CI 打开播放窗口，同时 GPIO43 拉高
```

### 5.2 录音门控（重要）

CI 侧的判断是一行：

```c
if (is_wake_up_flag || is_always_iis_flag)
```

- `is_wake_up_flag`：CI 自己的唤醒态，受 `EXIT_WAKEUP_TIME` 控制；
- `is_always_iis_flag`：只由 `0x011A` 置真、`0x011B` 置假。

**退出唤醒态不会停录音**，只要 `is_always_iis_flag` 为真，I2S 上就一直有 PCM。唤醒态超时已通过 `0x0113` 改成 65535 秒（≈18 小时，不能发 0，会触发 FreeRTOS 断言）。

### 5.3 日志速查

| 标记 | 含义 |
|---|---|
| `[AUDIO-IN ]` | 上行：收到的字节/期望、帧数、rms、peak、连续静音次数 |
| `[AUDIO-OUT]` | 下行：同格式 |
| `>>>>> [CI-EVT]` | CI 上报事件 |
| `>>>>> [CI-CMD]` / `<<<<< [CI-CMD]` | 下发/应答 |
| `PA ON/OFF (pin 43 = x)` | 功放使能变化 |

判读规则：

- `0/2048 B ... rms=0` 持续 → 上行断流（看门狗会重发 `START_RECORD`）；
- `2048/2048 B` 但 `rms≈0` → CI 没拾到人声（麦/增益/VAD），不是链路问题；
- `[CI-CMD] ... 失败` 反复 → UART 未确认，查接线与波特率；
- `SYS_READY` 在运行中再次出现 → CI 重启过，状态已清零并重发。

## 6. 遗留问题

1. **CI1302 运行中重启**：日志中多次出现 `SYS_READY`，推测为供电跌落、看门狗或 921600 干扰所致，尚未定位根因。
2. **Brownout**：需硬件侧确认电源与去耦。
3. **内存水位**：`free sram 107467 / minimal 95871`，比 ES8311 时期下降，需持续观察。
4. **下行短读**：CI 每隔一段少送约 16 ms 数据（`1024/2048 B ... ESP_ERR_TIMEOUT`），不影响语义但会增加抖动。
