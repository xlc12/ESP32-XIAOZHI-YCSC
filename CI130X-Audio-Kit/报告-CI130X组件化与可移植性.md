# CI130X 音频方案：组件化与可移植性报告

> 版本：v1.0（2026-11-01）
> 代码基线：`main/audio/codecs/ci130x_protocol.*`、`main/audio/codecs/ci130x_audio_codec.*`、`main/boards/ycsc-esp32s3-8311-wgxl-cat/`
> 配套技能：`ci130x-audio-port`（`.trae/skills/ci130x-audio-port/`）
> 相关文档：《报告-CI130X音频移植与调试.md》（实现细节、日志判读、故障对照）

---

## 0. 结论摘要（TL;DR）

1. **不需要打成一个 `.a` 静态库**。真正值得复用的是「协议层 + I2S/UART 驱动」，它们可以做成标准 ESP-IDF 组件；`AudioCodec` 适配层必须留在小智工程的 `main` 里。
2. **当前耦合是可控的**：`ci130x_protocol.*` 零小智依赖，`ci130x_audio_codec.*` 只依赖一个薄抽象类；真正的移植成本集中在板级胶水、构建登记和 `sdkconfig` 行为配置。
3. **推荐三层结构**：
   - `components/ci130x_voice/`：纯驱动组件（UART 协议 + I2S 从机 + 功放/状态同步），零小智依赖；
   - `main/audio/codecs/ci130x_audio_codec.*`：约 60 行适配器，只做 `AudioCodec` 接口转发；
   - `main/boards/common/ci130x_board_glue.*`：把 `Application` / `DeviceStateEventManager` 桥接收口，新板只传引脚。
4. **移植成本**：
   - 移植到另一块小智板：5 处改动，约 100 行（含胶水）；
   - 移植到非小智 ESP-IDF 工程：复用组件即可，无需 `AudioCodec`；
   - 纯复制现有代码（不拆组件）：2 个 `.cc` + 2 个头文件 + 2 行 CMake + 约 50 行板级胶水。
5. **最大风险点**：`AudioCodec` 头文件反向依赖 `board.h`（组件不能依赖 `main`）、静态唤醒回调单实例、以及 `sdkconfig` / `config.json` 的构建符号漂移。

### 1.2 依赖图

```text
Application / AudioService
        │
        ▼
   AudioCodec (main/audio/audio_codec.h)   ← 纯抽象，但 include 了 board.h
        ▲
        │ 继承
 Ci130xAudioCodec (main/audio/codecs/)
        │
        ├── Ci130xProtocol ──► ESP-IDF: driver/uart, FreeRTOS, esp_log
        │
        └── ESP-IDF: driver/i2s_std, driver/gpio, esp_timer

Board::GetAudioCodec() ──► Application::WakeWordInvoke
                       └─► DeviceStateEventManager（idle / speaking / listening）
```

关键事实：

- `ci130x_protocol.{h,cc}` 只包含 `driver/uart.h`、FreeRTOS、`esp_log.h`，**没有任何小智头文件**（见 [ci130x_protocol.h](../../main/audio/codecs/ci130x_protocol.h)）。
- `ci130x_audio_codec.h` 只包含 `audio_codec.h` 和 `ci130x_protocol.h`。
- `audio_codec.h` 本身 `#include "board.h"`，所以**任何继承 `AudioCodec` 的代码都不能放进 `components/`**（ESP-IDF 组件不能依赖 `main`）。
- 板级胶水直接使用 `Application`、`Board::GetInstance()`、`DeviceStateEventManager`、`kDeviceState*`，这是耦合度最高的部分。

## 2. 耦合度评估

### 2.1 逐文件评分

评分口径：**独立度** = 去掉小智工程后还能原样复用的比例。

| 位置 | 依赖 | 独立度 | 移植动作 |
|---|---|---|---|
| `ci130x_protocol.h/.cc` | 仅 ESP-IDF UART / FreeRTOS | 95% | 原样搬进组件 |
| `ci130x_audio_codec.h/.cc` | `AudioCodec`、`AUDIO_CODEC_DMA_DESC_NUM` | 70% | 抽成 `Ci130xAudio` 纯驱动 + 60 行适配器 |
| 板级 `GetAudioCodec()` | `Application`、`Board`、`DeviceStateEventManager` | 10% | 重写约 50 行，收口成 glue |
| 板级 `config.h` | 引脚/采样率宏 | 0% | 按新板重新定义 |
| `main/CMakeLists.txt` | 手工源文件列表 | 0% | 2 行登记（或由组件自动编译） |
| `Kconfig.projbuild` | 板型 choice、`USE_DEVICE_AEC` depends | 0% | 新板加符号 |
| `config.json` / `sdkconfig` | `USE_SERVER_AEC`、`USE_AFE_WAKE_WORD`、SR 模型 | 0% | 逐项核对 |
| `DeviceStateEventManager` 行为（EXP-004） | 小智状态机 | 0% | 保留原行为，做成 glue 的可选项 |

### 2.2 `AudioCodec` 契约面

适配器只需要满足下面这些成员，CI130X 的业务逻辑可以完全放在组件里：

| 基类成员 | 谁在用 | 说明 |
|---|---|---|
| `Read(int16_t*, int)` / `Write(const int16_t*, int)` | `InputData()` / `OutputData()` | 唯一的音频数据入口 |
| `EnableInput/EnableOutput(bool)` | `AudioService` 电源管理 | 需要转发到 CI 的 `0x011A/0x011B` 和 `0x0220` |
| `SetOutputVolume(int)` | 设置页 / NVS | 0~100 映射到 CI 的 1~7 档 |
| `duplex_` | 框架判定全双工 | CI 方案必须为 `true` |
| `input_reference_` | AFE 参考通道 | CI 方案为 `false` |
| `input_channels_` / `output_channels_` | 声道数 | 都是 1，立体声拆解在 `Read/Write` 里做 |
| `input_sample_rate_` / `output_sample_rate_` | AFE / 重采样 | 都必须是 16000，且相等 |
| `tx_handle_` / `rx_handle_` | `AudioCodec::Start()` 使能 I2S | 驱动需要把句柄交给适配器 |
| `output_enabled_` / `input_enabled_` | 基类状态、PA 控制 | 由基类维护，适配器读取 |

对应代码：`main/audio/audio_codec.h` 第 18~57 行、`main/audio/audio_codec.cc` 第 17~48 行。

### 2.3 隐性耦合（按风险排序）

| # | 问题 | 位置 | 影响 |
|---|---|---|---|
| 1 | `audio_codec.h` 反向依赖 `board.h` | `audio_codec.h` 第 12 行 | codec 无法直接组件化，必须留适配器在 `main` |
| 2 | 唤醒回调是 `static std::function` | `ci130x_audio_codec.h` 第 39、73 行 | 一个固件只能有一个实例；组件化后要改成实例回调 |
| 3 | 板级用 `static bool` 防重复注册 | 板级文件第 457~481 行 | `GetAudioCodec()` 重复调用时行为依赖静态状态 |
| 4 | I2S 时序假设 | `ci130x_audio_codec.cc` 第 125~182 行 | 必须是从机、16 bit 数据 / 32 bit slot、立体声、16 kHz；换目标芯片可能不成立 |
| 5 | 采样率必须相等 | 构造函数 `assert` | 不支持输入输出不同采样率 |
| 6 | EXP-004 半双工实验写死在板级 | 板级文件第 468~479 行 | 与服务端实时打断（server AEC）语义冲突，移植时容易照抄出问题 |
| 7 | `sdkconfig.defaults` 板型符号不一致 | `sdkconfig.defaults` 第 85 行 `..._TEST` vs Kconfig `..._WGXL_CAT` | 照抄 default 会选不中板子 |
| 8 | `config.json` 也写的是 `..._TEST` | `config.json` 第 8 行 | 与 `sdkconfig` 实际值不一致，构建结果依赖已有 `sdkconfig` |
| 9 | 行为依赖 `CONFIG_USE_SERVER_AEC` / `CONFIG_USE_AFE_WAKE_WORD` | `config.json` 第 14~20 行 | 只复制代码、不带配置，会出现“能编译但交互不对” |
| 10 | 日志被 AFE / LVGL 淹没 | 全局 log level | 没有统一日志策略时，音频问题很难定位 |

### 2.4 耦合结论

- **可复用内核**：UART 协议 + I2S 从机读写 + 状态同步 + 看门狗，约 800 行，逻辑完整、边界清晰。
- **不可复用外壳**：`AudioCodec` 继承、板级引脚、`Application` 唤醒/状态桥接、构建登记、行为配置。
- 因此正确的打包方式是「**抽出内核 + 保留薄外壳**」，而不是把整个 codec 塞进组件。

## 3. 目标架构

### 3.1 三层划分

| 层 | 位置 | 依赖 | 职责 | 禁止事项 |
|---|---|---|---|---|
| L1 驱动组件 | `components/ci130x_voice/` | 仅 ESP-IDF | 协议、I2S、PA、音量、状态同步、看门狗 | 不得包含 `AudioCodec`、`Application`、`board.h` |
| L2 适配器 | `main/audio/codecs/ci130x_audio_codec.*` | L1 + `AudioCodec` | 继承 `AudioCodec`，转发 4 个虚函数，填基类字段 | 不得再写业务逻辑 |
| L3 板级胶水 | `main/boards/common/ci130x_board_glue.*` | L2 + `Application` | 唤醒桥接、设备状态桥接、EXP-004 开关 | 不得包含引脚定义 |

### 3.2 目录树

```text

│   └── ci130x_voice/
│       ├── CMakeLists.txt
│       ├── idf_component.yml

│       │   ├── ci130x_protocol.h

│       └── src/
│           ├── ci130x_protocol.cc
│           └── ci130x_audio.cc
├── main/
│   ├── audio/codecs/
│   │   ├── ci130x_audio_codec.h      # 适配器
│   │   └── ci130x_audio_codec.cc     # 约 60 行

│           ├── config.h              # 只留引脚宏
│           └── ycsc_esp32s3_8311_wgxl_cat.cc
└── ...
```

### 3.3 各层边界

- L1 里所有引脚通过运行时 `Config` 结构体传入，**不使用 Kconfig 定义引脚**；这样同一份组件可以服务多块板。
- L2 只负责“翻译”，不改动 `AudioService` 的任何调用方式。
- L3 负责“小智语义”，把 `WAKE_UP`、`idle`、`speaking`、`listening` 这些状态映射到 L1 的开关。

## 4. 组件设计

### 4.1 运行时配置（替代板级宏）

```cpp
// components/ci130x_voice/include/ci130x_audio.h
struct Ci130xConfig {
    uart_port_t uart_port   = UART_NUM_1;
    gpio_num_t  uart_tx     = GPIO_NUM_NC;
    gpio_num_t  uart_rx     = GPIO_NUM_NC;
    int         uart_baud   = 921600;

    gpio_num_t  bclk        = GPIO_NUM_NC;  // CI 输出
    gpio_num_t  ws          = GPIO_NUM_NC;  // CI 输出
    gpio_num_t  dout        = GPIO_NUM_NC;  // ESP32 -> CI
    gpio_num_t  din         = GPIO_NUM_NC;  // CI -> ESP32

    gpio_num_t  pa_pin        = GPIO_NUM_NC;
    bool        pa_active_high = true;
    int         sample_rate    = 16000;
};
```

I2S 的 MCLK 固定为 `I2S_GPIO_UNUSED`（CI 主机的 MCLK 不接 ESP32），不放进配置。

### 4.2 公开 API

```cpp
enum class Ci130xEvent {
    kSysReady, kSysError, kWakeUp, kExitWakeUp, kVadStart, kPcmFinish,
};

class Ci130xAudio {
public:
    using EventCallback = std::function<void(Ci130xEvent, const uint8_t*, uint16_t)>;

    explicit Ci130xAudio(const Ci130xConfig& cfg);
    ~Ci130xAudio();

    // 音频数据
    int  Read(int16_t* dest, int samples);
    int  Write(const int16_t* data, int samples);

    // 控制
    void SetOutputVolume(int volume);      // 0~100 -> 1~7
    void EnableInput(bool enable);         // 0x011A / 0x011B
    void EnableOutput(bool enable);        // 0x0220 + PA
    void SetUplinkEnabled(bool enable);    // 只切 CI 上行，不动 ESP32 读
    void RequestExitWakeUp();              // 0x010D，异步
    void SetEventCallback(EventCallback cb);

    // 供适配器使用
    i2s_chan_handle_t tx_handle() const;
    i2s_chan_handle_t rx_handle() const;
};
```

与现有实现的映射：

| 现有成员 | 迁移到 | 处理方式 |
|---|---|---|
| `Ci130xProtocol::SendCommand` | `Ci130xProtocol` | 原样保留 |
| `Ci130xAudioCodec::Read/Write` | `Ci130xAudio` | 去掉 `override`，逻辑不变 |
| `EnableInput/EnableOutput/SetOutputVolume` | `Ci130xAudio` | 逻辑不变 |
| `SyncWithChip` / `SyncTask` | `Ci130xAudio`（private） | 逻辑不变 |
| `SetChipUplinkEnabled` / `RequestExitWakeUp` | `Ci130xAudio` | 逻辑不变 |
| `SetWakeWordHandler`（static） | **删除** | 改为 `SetEventCallback` 实例回调 |
| `CreateDuplexChannels` | `Ci130xAudio::Init` | 逻辑不变 |
| `duplex_`、`input_reference_`、采样率等 | 适配器 | 由适配器设置基类字段 |
| `pa_pin_`、`pa_active_high_` | `Ci130xConfig` | 不再从板级宏传入构造函数参数列表 |

### 4.3 事件模型

L1 只上报语义事件，不关心小智状态：

| CI 事件 | L1 枚举 | L3 动作 |
|---|---|---|
| `0x0601` | `kSysReady` | 强制全量重发 |
| `0x0102` | `kWakeUp` | `Application::WakeWordInvoke()`（仅在 idle / speaking） |
| `0x0109` | `kExitWakeUp` | 补一次录音门控重发 |
| `0x0108` | `kVadStart` | 只记日志（可接 LED） |
| `0x0106` | `kPcmFinish` | 只记日志（可接 LED） |
| `0x0602` | `kSysError` | 日志 / 重试 |

### 4.5 适配器（留在 main）

```cpp
// main/audio/codecs/ci130x_audio_codec.h
#pragma once

#include "audio_codec.h"
#include "ci130x_audio.h"

class Ci130xAudioCodec : public AudioCodec {
public:
    explicit Ci130xAudioCodec(const Ci130xConfig& cfg);

    void SetEventCallback(Ci130xAudio::EventCallback cb);
    void SetUplinkEnabled(bool enable);
    void RequestExitWakeUp();

    void SetOutputVolume(int volume) override;
    void EnableInput(bool enable) override;
    void EnableOutput(bool enable) override;

protected:
    int Read(int16_t* dest, int samples) override;
    int Write(const int16_t* data, int samples) override;

private:
    Ci130xAudio audio_;
};
```

实现要点：

- 构造函数里设置 `duplex_ = true; input_reference_ = false; input_channels_ = output_channels_ = 1;`，采样率取 `cfg.sample_rate`；
- 把 `audio_.tx_handle()` / `rx_handle()` 赋给基类的 `tx_handle_` / `rx_handle_`，保证 `AudioCodec::Start()` 能正常使能通道；
- 不覆盖 `Start()`，继续复用基类的 NVS 音量加载逻辑；
- `SetOutputVolume/EnableInput/EnableOutput` 先调用基类再转发给 L1（保持原有顺序）。

### 4.6 板级胶水（跨板复用）

```cpp
// main/boards/common/ci130x_board_glue.h
#pragma once
#include "codecs/ci130x_audio_codec.h"

struct Ci130xGlueOptions {
    bool wake_word_enabled        = true;
    bool exit_wakeup_on_idle      = true;
    bool stop_uplink_while_speaking = false;  // EXP-004；默认关
};

class Ci130xBoardGlue {
public:
    static void Attach(Ci130xAudioCodec& codec, const Ci130xGlueOptions& opt = {});
};
```

实现要点：

1. 用 `Attach` 里的 `static Ci130xAudioCodec* s_codec` 保存实例，避免状态回调里再次调用 `Board::GetInstance().GetAudioCodec()` 造成递归/重复构造。
2. `kSysReady` → 全量重发；`kWakeUp` → 只在 `Idle` / `Speaking` 调 `WakeWordInvoke`；`Idle` → `RequestExitWakeUp()`。
3. `stop_uplink_while_speaking` 对应现在的 EXP-004：`Speaking` 关、`Listening` 开。**默认关闭**，因为实时打断需要播报期间持续上行。
4. 只注册一次（`static bool`），或由 `main.cc` 在板子初始化后显式调用一次。

新板的 `GetAudioCodec()` 最终只剩：

```cpp
virtual AudioCodec* GetAudioCodec() override {
    static Ci130xAudioCodec codec({
        .uart_port = CI130X_UART_PORT,
        .uart_tx   = CI130X_UART_TX_PIN,
        .uart_rx   = CI130X_UART_RX_PIN,
        .uart_baud = CI130X_UART_BAUD_RATE,
        .bclk = AUDIO_I2S_GPIO_BCLK,
        .ws   = AUDIO_I2S_GPIO_WS,
        .dout = AUDIO_I2S_GPIO_DOUT,
        .din  = AUDIO_I2S_GPIO_DIN,
        .pa_pin = CI130X_PA_PIN,
        .pa_active_high = CI130X_PA_ACTIVE_HIGH,
        .sample_rate = AUDIO_INPUT_SAMPLE_RATE,
    });
    Ci130xBoardGlue::Attach(codec);
    return &codec;
}
```

## 5. 分阶段重构步骤

每一步都应可独立编译、可回滚；不要一次性大改。

### Step 0：建立基线

- 打 tag 或记录当前 commit；
- 保存一份可用的 `sdkconfig`；
- 记录当前行为基线：唤醒、对话、打断、音量、待机 PA 关闭。

### Step 1：协议层进组件（0 风险）

- 新建 `components/ci130x_voice/`；
- 把 `ci130x_protocol.h` 移到 `include/`，`ci130x_protocol.cc` 移到 `src/`；
- `main/CMakeLists.txt` 删除 `audio/codecs/ci130x_protocol.cc` 一行；
- 适配器头文件改成 `#include "ci130x_protocol.h"`（组件头文件路径自动可见）。

验证：`idf.py build` 通过，运行行为不变。

### Step 2：抽纯驱动 `Ci130xAudio`

按 4.2 的映射表搬运；这一步只改命名/归属，不改逻辑。

验证：编译通过；`Read/Write` 日志仍按原频率输出。

### Step 3：适配器瘦身

`ci130x_audio_codec.cc` 缩到 60 行左右，只保留转发和基类字段初始化。

验证：唤醒、对话、音量、PA 行为不变。

### Step 4：胶水收口

- 新增 `boards/common/ci130x_board_glue.*`；
- 板级 `GetAudioCodec()` 改成 4.6 的形式；
- EXP-004 改成 `Ci130xGlueOptions::stop_uplink_while_speaking`。

验证：状态切换日志与基线一致；`idle` 能收到 `0x010D`。

### Step 5：配置收敛

- 板级 `config.h` 只保留引脚与采样率；
- 删除 `AUDIO_CODEC_CI130X_ENABLE` 的双分支，改为构建期选择（或在板级直接返回 CI codec）；
- 修正 `sdkconfig.defaults` / `config.json` 的板型符号；
- 明确 `USE_SERVER_AEC` / `USE_DEVICE_AEC` / `USE_AFE_WAKE_WORD` 的组合。

验证：`idf.py fullclean && idf.py build` 后行为仍一致。

### Step 6：打包分发

- 给组件加 `idf_component.yml`、README、CHANGELOG；
- 打 `v0.1.0` tag；
- 其他工程通过 `EXTRA_COMPONENT_DIRS` 或 git 依赖引用。

## 6. 移植 Checklist

### 6.1 硬件

- [ ] CI1302/CI1306 的 SCLK / LRCLK / SDO / SDI 方向与 `config.h` 一致；
- [ ] CI 的 MCLK 不接 ESP32（ESP32 不驱动 MCLK）；
- [ ] UART TX/RX 交叉连接，波特率 921600；
- [ ] UART 引脚不与 UART0 控制台、PSRAM、Flash 冲突；
- [ ] 功放使能脚确认是「CI 的 PC4 + 0x0119」还是「ESP32 GPIO + 极性」；
- [ ] 扬声器与麦克风不在结构上形成强反馈（否则服务端 AEC 也难消）。

### 6.2 CI 侧固件

- [ ] `IIS_UPLOAD_IS_WAKEUP` / `IIS_DOWNLOAD_BY_CMD` 宏已启用；
- [ ] 唤醒词模型与提示音配置正确；
- [ ] 串口协议版本与 `ci130x_protocol.h` 的命令表一致；
- [ ] CI 上电会主动上报 `0x0601`（ESP32 可能错过，逻辑不能依赖它）。

### 6.3 工程配置

- [ ] `AUDIO_INPUT_SAMPLE_RATE == AUDIO_OUTPUT_SAMPLE_RATE == 16000`；
- [ ] `config.h` 中 I2S 四根线、UART 三参数、PA 宏已改；
- [ ] `main/CMakeLists.txt` 已登记适配器源文件（组件源文件不需要）；
- [ ] `Kconfig.projbuild` 已加板型符号（如果新增板）；
- [ ] `sdkconfig.defaults` 与 `config.json` 的板型符号一致；
- [ ] `CONFIG_USE_AUDIO_PROCESSOR=y`（AFE 输入需要 16k 单声道）；
- [ ] AEC 模式明确：`USE_SERVER_AEC` 或 `USE_DEVICE_AEC` 二选一；
- [ ] 唤醒词策略明确：CI 唤醒 + AFE 唤醒是否同时开启。

### 6.4 构建系统

- [ ] `components/ci130x_voice/` 被自动发现（或加入 `EXTRA_COMPONENT_DIRS`）；
- [ ] `main` 能包含 `ci130x_audio.h`（main 自动依赖所有组件）；
- [ ] 组件 `CMakeLists.txt` 的 `REQUIRES` 包含 I2S/UART/GPIO 驱动；
- [ ] 目标芯片为 `esp32s3` / `esp32p4`（当前 I2S 字段依赖 `SOC_I2S_HW_VERSION_2`）。

### 6.5 行为验证顺序

1. 串口能收到 `0x0601` 与事件帧 → UART 与校验正确；
2. 下发 `0x011A` 后 `[AUDIO-IN]` 持续有非零 PCM → I2S 方向与时序正确；
3. 说唤醒词出现 `WAKE_UP` 且进入 listening → 唤醒桥接正确；
4. 云端回复能听到声音 → 下行 + `0x0220` 播放窗口正确；
5. 空口 15 秒后出现 `PA OFF` → 电源管理正确；
6. 播报期间不断流、无重启 → 上行并发与状态机正确；
7. 打断行为符合预期（服务端 AEC 模式下需确认时间戳对齐）。

### 6.6 常见故障速查

| 现象 | 优先检查 |
|---|---|
| 完全没有 `[AUDIO-IN]` 非零数据 | CI 是否 `0x011A`；I2S 方向；DMA 描述符是否整除 |
| `Ringbuffer of AFE(FEED) is full` | `Read()` 是否按采样率补齐节奏 |
| 再喊唤醒词会话被掐断 | 唤醒回调是否只在 idle / speaking 放行 |
| 播报无声、文字正常 | 设备状态是否被提前切到 listening（音频会被丢弃） |
| 播报期间重启 | 上行并发、AFE、供电；先看是否 `0x0601` 重复上报 |
| 有回声/误打断 | 是否开了 server AEC 但上行被半双工掐断 |

更细的日志判读见 `references/troubleshooting.md`。

## 7. 分发方式

| 方式 | 适用场景 | 做法 |
|---|---|---|
| 本仓库 `components/` | 本工程长期维护 | 组件目录直接放入 `components/ci130x_voice/`，自动编译 |
| `EXTRA_COMPONENT_DIRS` | 多个本地工程共享 | 在顶层 `CMakeLists.txt` 指定组件根目录 |
| Git 依赖 | 跨团队/跨仓库 | `main/idf_component.yml` 写 `dependencies: ci130x_voice: {git: "...", path: "components/ci130x_voice", version: "v0.1.0"}` |
| 组件注册表 | 公开分发 | `compote component upload`，消费端按名字+版本依赖 |

版本策略建议：

- 组件版本只跟随「协议 + 驱动」的破坏性变更；
- 适配器/胶水留在宿主工程，各自跟随宿主；
- `CHANGELOG.md` 里记录：命令字变化、I2S 参数变化、事件枚举变化。

## 8. 风险与回滚

| 风险 | 概率 | 影响 | 缓解 |
|---|---|---|---|
| 组件化后 `AudioCodec` 引用断裂 | 中 | 编译失败 | 适配器必须留在 `main` |
| 静态唤醒回调改成实例回调引入时序问题 | 中 | 唤醒丢失/重复 | 保留原有状态过滤条件，灰度验证 |
| EXP-004 行为被默认关闭 | 高 | 播报期间上行恢复，可能重启 | 先保持默认 `true`，稳定后再评估 |
| `sdkconfig` 未随代码迁移 | 高 | 能编译但交互异常 | 提供 `sdkconfig.defaults` 片段 |
| 其他目标芯片 I2S 不兼容 | 中 | 音频异常 | `targets` 限定 S3/P4 |
| 组件与宿主版本漂移 | 低 | 行为不一致 | semver + tag + CHANGELOG |

回滚策略：Step 1~6 每一步独立提交；组件化失败时直接 revert 对应 commit，不影响 Step 0 基线。
